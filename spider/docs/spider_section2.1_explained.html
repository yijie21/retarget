SPIDER — The Method (Sections 2.1–2.3), Explained

Problem formulation, sampling-based MPC, and curriculum virtual contact guidance — every equation explained term by term, with the matching code from this repo. arXiv:2511.09484

Your intuition is correct: the whole thing just says “minimize the distance between the robot's state and the human trajectory.” The formalism only adds two refinements: (1) the “distance” is a per‑DOF weighted sum so different body parts matter differently, and (2) a physics constraint forces every state to be physically reachable rather than just copied.

The objective (Eq. 1)

\[ \min_{u_{0:T-1}}\; J(u_{0:T-1}) \;=\; \underbrace{\lVert x_T - x_T^{\text{ref}}\rVert^2_{Q_T}}_{\text{terminal term}} \;+\; \sum_{t=0}^{T-1}\Big( \underbrace{\lVert x_{t+1} - x_{t+1}^{\text{ref}}\rVert^2_{Q_t}}_{\text{tracking term}} \;+\; \underbrace{\lVert u_t \rVert^2_{R_t}}_{\text{control term}} \Big) \]

Eq. 1a — the cost to minimize

\[ \text{subject to}\quad x_{t+1} = f(x_t, u_t, t), \quad \forall t \in \{0,\dots,T-1\} \]

Eq. 1b — dynamics constraint (the simulator)

\[ x_{0:T} \in \mathcal{X}, \qquad u_{0:T-1} \in \mathcal{U} \]

Eq. 1c — feasibility constraints (joint / actuator limits)

The reference state decomposes into robot + object

\[ x_t^{\text{ref}} = \{q_t^{\text{ref}}, \dot q_t^{\text{ref}}\}, \qquad q_t^{\text{ref}} = \{\, q_t^{\text{ref,robot}},\; q_t^{\text{ref,object}} \,\} \] \[ q_t^{\text{ref,joint}} \in \mathbb{R}^{n_u}, \qquad T_t^{\text{ref,base}} \in SE(3), \qquad q_t^{\text{ref,object}} \in SE(3) \]

So the reference is the human's joint angles, the base/wrist pose (in \(SE(3)\), i.e. position + 3D rotation), and the object pose (also \(SE(3)\)).

The three terms, in plain English

1. Tracking term — \(\sum_t \lVert x_{t+1}-x_{t+1}^{\text{ref}}\rVert^2_{Q_t}\)

“At every timestep, stay close to the human trajectory.” This is the bulk of the cost.

2. Terminal term — \(\lVert x_T - x_T^{\text{ref}}\rVert^2_{Q_T}\)

“And especially nail the final state.” Same distance, applied to the last step, usually weighted more strongly.

3. Control term — \(\lVert u_t\rVert^2_{R_t}\)

“Don't use wild or expensive actions.” A regularizer encouraging smooth, low-effort motion.

The notation that usually trips people up: \(\lVert v\rVert^2_Q\)

A weighted norm is just a weighted sum of squares. For a diagonal \(Q\):
\[ \lVert v\rVert^2_Q \;=\; v^\top Q\, v \;=\; \sum_i Q_{ii}\, v_i^2 \]

It is not a plain Euclidean distance — each coordinate \(v_i\) is scaled by its own weight \(Q_{ii}\) before summing. Here \(Q_t=\operatorname{diag}(\{q_{\text{robot}},q_{\text{object}}\})\) means “weight robot DOFs by these numbers, object DOFs by those.” That diagonal is the per-DOF weight vector in the code:

delta_qpos = qpos_diff * qpos_weight              # element-wise weighting  ← this is Q
qpos_dist  = torch.norm(delta_qpos, p=2, dim=1)   # then the L2 norm
qpos_rew   = -qpos_dist                            # cost = -reward

And the weights come straight from the config:

The tiny 0.003 on finger joints vs. 1.0 on object position is exactly the \(Q\) matrix saying: “I care far more about the object ending up in the right place than about each finger joint matching the human precisely” — sensible given the embodiment gap.

Rotation detail: for rotation DOFs the “\(x-x^{\text{ref}}\)” is not plain subtraction. Because base and object poses live in \(SE(3)\), the code uses quat_sub (the geodesic difference on the rotation manifold \(SO(3)\)) instead of subtracting numbers.

The constraint that makes it “physics-based”

\[ x_{t+1} = f(x_t, u_t, t) \]

This single line is what separates SPIDER from plain kinematic retargeting. \(f\) is the physics simulator. It says: you don't get to place the robot wherever minimizes the distance — you only pick actions \(u_t\), and the next state is whatever physics produces. If the fingers don't actually grip the object, gravity drops it, \(x_{t+1}\) diverges from \(x_{t+1}^{\text{ref}}\), and the cost rises. Dynamic feasibility is enforced by the constraint, not by the cost.

The whole formula in one sentence:
Choose the action sequence that keeps the physically-simulated robot trajectory as close as possible (in a per-DOF weighted sense, caring most about object pose and the final state) to the human reference, while obeying physics and actuator limits.

Section 2.2 — How it's actually solved: sampling-based MPC

There's no closed-form solution — \(f\) is a non-differentiable, contact-rich simulator, so you can't take gradients of \(J\). SPIDER instead solves Eq. 1 by sampling: try many random control sequences, simulate them all, and move toward the good ones. This is the MPPI / DIAL-MPC family.

The update rule (Eq. 2)

\[ U^{i+1} \;=\; U^{i} \;+\; \frac{\displaystyle\sum_{j=1}^{N_W} \exp\!\big(-J(U^{i}+[W]_j)/\lambda\big)\,[W]_j} {\displaystyle\sum_{j=1}^{N_W} \exp\!\big(-J(U^{i}+[W]_j)/\lambda\big)} \]

Eq. 2 — softmax-weighted control update (one optimization iteration)

Read it as a three-step loop, repeated for iterations \(i=0,1,2,\dots\):

SymbolMeaningIn the code
\(U^i\)The current best-guess control sequence at iteration \(i\) (the whole horizon).ctrls
\([W]_j\)The \(j\)-th random noise perturbation added to \(U^i\), drawn \([W]_j \sim \mathcal{N}(0,\Sigma)\).delta_ctrl_samples
\(N_W\)Number of sampled particles (candidate trajectories).num_samples = 2048
\(J(\cdot)\)Trajectory cost from Eq. 1a — computed by rolling each candidate through the simulator.-rews (cost = −reward)
\(\lambda\)Temperature. Small \(\lambda\) → sharp, greedy weighting; large \(\lambda\) → soft averaging.temperature = 0.3

Step 1 — sample. Draw \(N_W\) noise vectors and add each to the current guess: \(U^i + [W]_j\). In code the noise is drawn at sparse knot points and interpolated to the full horizon (smoother, fewer dimensions to sample):

knot_samples       = torch.randn_like(noise_scale) * noise_scale * global_noise_scale  # ← [W]_j
delta_ctrl_samples = interp(knot_samples, knot_steps)
ctrls_samples      = ctrls + delta_ctrl_samples                                        # ← U^i + [W]_j

Step 2 — weight. Roll out all \(N_W\) candidates through physics, get cost \(J\) for each, and turn costs into weights with a softmax: \(w_j \propto \exp(-J_j/\lambda)\). Low cost → high weight.

top_rews_normalized = (top_rews - top_rews.mean()) / (top_rews.std() + 1e-2)
top_weights = F.softmax(top_rews_normalized / temperature, dim=0)   # ← exp(-J/&lambda) / Σ exp(-J/&lambda)
Code vs. paper: Eq. 2 sums over all \(N_W\) particles. The implementation only keeps the top 10% by reward before the softmax (torch.topk), and standardizes them first. Same idea (CEM-style elite weighting), just a more stable practical variant.

Step 3 — update. The new guess is the old one plus the weighted average of the perturbations — exactly the fraction in Eq. 2:

ctrls_mean = (weights[:, None, None] * ctrls_samples).sum(dim=0)    # ← U^(i+1)

The annealing schedule (Eq. 3)

\[ \Sigma_h^{i} \;=\; \exp\!\left(-\frac{N-i}{\beta_1 N} \;-\; \frac{H-h}{\beta_2 H}\right) I \]

Eq. 3 — how the sampling covariance shrinks

\(\Sigma_h^i\) is the noise covariance used at iteration \(i\) and horizon step \(h\). The two exponential terms make the search anneal — start broad (explore), end narrow (refine) — along two independent axes:

TermEffectIn the code
\(-\dfrac{N-i}{\beta_1 N}\)Outer-iteration decay. Early iterations (\(i\) small) → large noise; later iterations (\(i\to N\)) → small noise. \(\beta_1\) controls how fast.global_noise_scale = beta_traj**i
with beta_traj = final_noise_scale**(1/max_num_iterations)
\(-\dfrac{H-h}{\beta_2 H}\)Temporal decay. Near-future steps (\(h\) small) get explored harder; far-future steps get less noise. \(\beta_2\) controls the falloff.torch.logspace(first_ctrl_noise_scale, last_ctrl_noise_scale, steps=horizon/knot_dt)

So the paper's single \(\Sigma_h^i\) is, in code, a product of two factors: a per-knot logspace profile over the horizon (\(h\)) times a geometric per-iteration factor beta_traj**i (\(i\)). Both shrink toward the end — exactly the “broad → targeted” refinement Eq. 3 describes.

Section 2.2 in one sentence: repeatedly perturb the control sequence with shrinking noise, simulate thousands of perturbations in parallel, and step toward a softmax-weighted average of the cheapest ones — run inside a receding-horizon MPC loop.

Section 2.3 — Curriculum virtual contact guidance

This is the paper's key novelty. Problem: pure sampling struggles with contact-rich manipulation — if the hand never randomly stumbles onto a stable grasp, the object falls, every sample looks equally bad, and there's no gradient of progress to climb. Idea: early on, “cheat” by virtually holding the object near its reference pose, giving the sampler a feasible neighborhood to explore; then gradually remove the help so the final motion is purely physical.

The guided constraint (Eq. 4)

\[ c_{k,t}\,\big\lVert\, {}^{\text{robot}}p_{k,t}^{\text{object}} \;-\; {}^{\text{robot}}p_{k,t}^{\text{object,ref}} \,\big\rVert_2^2 \;\le\; \eta_i \]

Eq. 4 — virtual contact constraint, relaxed by the curriculum

\[ c_{k,t} \;=\; \mathbb{1}\!\left(\big\lVert {}^{\text{robot}}p_{k,t}^{\text{object,ref}} \big\rVert_2 \le \varepsilon_{\text{contact}}\right) \]

contact indicator: 1 when reference says contact point k should be touching at time t

SymbolMeaningIn the code
\(c_{k,t}\)Contact indicator — 1 if reference contact point \(k\) is active at time \(t\), else 0. Only active contacts are guided.contact mask (from detect_contact.py)
\({}^{\text{robot}}p_{k,t}^{\text{object}}\)Current relative position between robot contact point \(k\) and the object.site_xpos at contact sites
\({}^{\text{robot}}p_{k,t}^{\text{object,ref}}\)Desired relative position from the reference.contact_pos reference
\(\eta_i\)Tolerance on the constraint at iteration \(i\). Small early (tight grip help), then \(\eta_i\to\infty\) as \(i\to N\) (constraint relaxes to nothing).encoded as actuator gain decay (below)
\(\varepsilon_{\text{contact}}\)Distance threshold for deciding a point is “in contact.”contact detection threshold

The constraint says: for each point the reference marks as in-contact, keep the robot–object relative geometry close to the reference, within tolerance \(\eta_i\). It effectively “sticks” the hand to the object during early optimization. Crucially this is not a soft reward term — it enlarges the feasible basin so the sampler is steered toward the correct contact sequence instead of having to discover it by luck.

The curriculum: how \(\eta_i\) is implemented (gain decay)

In code the constraint is realized with virtual object actuators (added to scene_act.xml by generate_xml.py) that pull the object toward its reference pose. Their stiffness \(K_p\) (and damping \(K_d\)) plays the role of tightness: high gain = tight constraint = small \(\eta\). The curriculum decays the gain geometrically each iteration and forces it to exactly zero on the last iteration — i.e. \(\eta_i\to\infty\), no help left:

for i in range(max_num_iterations):
    decay = guidance_decay_ratio ** i        # e.g. 0.5**i  → shrinking stiffness (η_i growing)
    kp_i = base_kp * decay
    kd_i = base_kd * decay
    if i == max_num_iterations - 1:
        kp_i = zeros_like(base_kp)            # final iter: guidance fully OFF (purely physical)
        kd_i = zeros_like(base_kd)
Verified, not assumed: at the start and end of a run the code asserts the object actuator gains are zero (_assert_object_actuator_gains_zero), guaranteeing the exported trajectory is held by the hand's own physics, not by the virtual helper. The helper exists only to shape the search during optimization.

There's also a direct nudge: at each control tick the hand's position targets are shifted toward the measured contact points (compute_contact_point_delta), clipped to ±1 cm, so the fingers move onto the contact locations while the curriculum is active.

Section 2.3 in one sentence: start optimization with a virtual “magnet” that keeps each active contact point glued to its reference (widening the feasible region for the sampler), then anneal that magnet's strength to zero so the final grasp is achieved by real physics alone.

The full method, end to end

  1. Eq. 1 (§2.1) defines what to optimize: weighted tracking of the human reference, subject to physics.
  2. Eq. 2–3 (§2.2) defines how: sampling-based MPC with softmax-weighted updates and annealed noise.
  3. Eq. 4 (§2.3) makes contact-rich tasks solvable: a curriculum virtual-contact constraint that widens the feasible basin early and vanishes by the end.

Human demos give the task structure; physics-based sampling grounds it in dynamic feasibility; virtual guidance preserves the contact intent — the three pieces of the paper's thesis.
