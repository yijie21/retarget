GeoRT — Geometric Retargeting How a human hand's motion is turned into robot-hand joint commands, in plain words. Based on the paper “Geometric Retargeting: A Principled, Ultrafast Neural Hand Retargeting Algorithm” and the code in this repo (trainer.py, model.py).

You found the paper light on method detail — that's because the real method lives in five geometric loss functions and two small neural networks. This page explains exactly what each one does and why.

1. The problem, in one breath

You move your hand. A robot hand (Allegro, Wuji, …) should copy the intent of that motion in real time. But the robot's fingers have different lengths, different joints, and a different reachable space than yours. Retargeting = the function that converts human fingertip positions → robot joint angles, frame by frame, so the robot "does what you mean."

The hard part: there is no ground-truth answer. Nobody can label "this human pose = exactly this robot pose." So GeoRT learns the mapping unsupervised, guided only by geometric common sense about what a good mapping should preserve.

What other methods do (and GeoRT's twist)

⏳ Optimization-based (e.g. DexPilot)

Solve a little optimization problem every single frame to find joint angles. Accurate but slow, and needs hand-tuned weights.

⚡ GeoRT

Train a tiny network once. At runtime it's a single forward pass → ~1 kHz (1000 retargets/sec). No per-frame optimization, far fewer knobs, no manual hand-pose labels.

2. The two networks

GeoRT splits the hand finger-by-finger. Each finger gets its own pair of small MLPs (model.py). They are inverses of each other:

IK MODEL — the thing we actually want
fingertip → joints Input: a 3D fingertip position. Output: that finger's robot joint angles. This is the retargeter you deploy. (IKModel)
↻
FK MODEL — a helper / “simulator”
joints → fingertip A learned, differentiable copy of the robot's real forward kinematics: given joint angles, where does the robot fingertip end up? (FKModel)

Why two networks instead of one?

To train the IK model we need to measure “if the robot uses these joints, where does its fingertip actually go?” — and we need that measurement to be differentiable so gradients can flow back into the IK network. The robot's true forward kinematics is a non-differentiable simulator (SAPIEN). So GeoRT first trains a neural network to imitate the real FK:

  • Sample 100k random robot joint configs, run the real simulator to get true fingertip positions (generate_robot_kinematics_dataset).
  • Train FKModel to reproduce them (plain MSE). This takes ~5 min and happens once per robot hand, then is frozen.

Now the training loop can do point → IK → joints → FK → point' entirely with differentiable neural nets. That round-trip is the backbone of every loss below.

The training round-trip (from trainer.py)

point          = a human fingertip position        # [B, 5 fingers, 3]
joint          = ik_model(point)                   # robot joint angles
embedded_point = fk_model(joint)                   # where robot fingertip lands

Everything GeoRT learns is just: “shape the IK network so that embedded_point behaves the way a good retargeting should.” The five rules for “behaves well” are the loss functions.

3. The training data: workspaces, not pose pairs

GeoRT never sees matched (human-pose, robot-pose) pairs. Instead it uses two clouds of points:

Human cloud — record yourself for a minute (or sample the MANO model): stretch each finger to its limits and do pinches. Keep only the 5 fingertips. This traces out the region of space your fingertips can reach.

Robot cloud — randomly wiggle the robot in simulation and record where its 5 fingertips land. This traces out the robot's reachable region.

Retargeting then becomes a geometry problem: find a mapping that warps the human's reachable region onto the robot's reachable region while preserving the structure of motion. That's literally what "Geometric Retargeting" means.

4. The five geometric rules (loss functions)

This is the heart of the paper. Each rule is one term in the training loss (trainer.py, lines ~276–335). Default weights shown on the right.

weight 80 — the dominant term

① Chamfer / Workspace coverage “use your whole range”

Push the cloud of robot fingertip positions (produced by mapping the human cloud) to cover the robot's true reachable cloud. Chamfer distance just measures “how well do two point clouds overlap.”

Why: guarantees the mapping uses the robot's entire workspace — when you fully open or fully close your hand, the robot does too, instead of cramming everything into a tiny middle region. This is the "C-space coverage" property from the abstract.

weight 1 (baseline)

② Direction / Motion fidelity “move the same way I do”

Nudge a human fingertip a tiny bit in some random direction. The robot fingertip should move in the same direction. The loss maximizes the cosine similarity between “human nudge” and “robot response” (it's written as a negative dot product of the two unit vectors).

Why: if you move your finger up-and-left, the robot finger moves up-and-left. This preserves the feel and intuitiveness of teleoperation — the single most important property for a human operator.

weight 0.1

③ Curvature / Flatness “respond smoothly, no jerks”

Take a point and its two neighbors a hair away on each side; the robot's response should be (almost) a straight line through them — i.e. the second derivative ≈ 0. Implemented as (f(x+δ) + f(x−δ) − 2·f(x))².

Why: makes the mapping locally linear and uniform, so equal hand motions give equal robot motions everywhere. No regions where the robot suddenly over-reacts or freezes. (The "high flatness / uniform response" property.)

weight 1

④ Pinch correspondence “if I pinch, the robot pinches”

Whenever two human fingertips touch (distance < 1.5 cm), force the corresponding two robot fingertips to also meet. Checked for every finger pair (in practice thumb-to-other matters most).

Why: pinching/grasping is where retargeting usually breaks — the robot "almost" touches and drops the object. This term makes contact line up precisely, so grasps transfer.

weight 0 — present but off in this repo

⑤ Self-collision avoidance “don't crash your own fingers”

A learned classifier flags joint configurations where the robot's fingers would collide, and the loss steers the IK network away from them. In the released code this term is stubbed out (w_collision = 0), but it's part of the principled formulation.

The whole objective is just their weighted sum

loss = direction_loss
     + 80.0 * chamfer_loss      # cover the workspace
     +  0.1 * curvature_loss    # stay smooth/flat
     +  1.0 * pinch_loss        # pinches line up
     +  0.0 * collision_loss    # (disabled here)

⚖️ This is the "principled, fewer hyperparameters" claim: the entire behavior of the retargeter is governed by these ~4 interpretable weights, each tied to a concrete geometric property — versus optimization-based methods that juggle many per-frame, hard-to-interpret cost terms.

Deploying it is three lines (from the README)

import geort
model = geort.load_model('geort_1')
qpos  = model.forward(mocap.get())   # human keypoints in → robot joints out

6. Why each buzzword in the title is true

ClaimWhere it comes from
GeometricEvery loss is a statement about shapes & directions in 3D space (cloud overlap, motion direction, flatness, contact), not about labeled examples.
Principled~4 interpretable weights, each mapped to one concrete property (coverage, fidelity, smoothness, pinch, collision). Unsupervised — no manual hand-pair annotation.
UltrafastInference is a single MLP pass per finger → ~1 kHz. No test-time optimization loop, unlike DexPilot-style methods.
NeuralTwo tiny MLPs per finger (IK + the FK surrogate that makes training differentiable).

7. The one-sentence summary

GeoRT trains a tiny per-finger network to map your fingertips to robot joints by enforcing five geometric common-sense rules — cover the robot's full range, move in the same direction you do, respond smoothly, match your pinches, and avoid self-collision — using a learned differentiable forward-kinematics model so it needs no labeled data, and then runs at 1 kHz with no per-frame optimization.
